# OdysseusBuffBars Architecture

## High-level architecture

OdysseusBuffBars has one production renderer authority: MANAGED. The ordinary legacy Bars backend, its secure cancellation overlays, and the direct-scanning Auras/Engine backend are retired:

- No `OBB.Engine`, direct legacy aura scanner, synthetic legacy weapon-enchantment scanner, legacy group/header/bar frame, secure overlay, or legacy runtime cache is loaded or creatable by OBB production code. The obsolete Core `OBB.groups`, `OBB.bars`, and `OBB.auraData` tables and Config's guarded `OBB.filterAuraRows`/`OBB.auraData` fallback are removed.
- The managed player-BUFFS production renderer uses an independent `CustomAuraContainer` with one `HELPFUL` group. Blizzard owns aura identity, duration, sorting, filtering, lifecycle, native tooltip, and native right-click cancellation; the addon owns static styling and the independent position/root frame.
- The managed player-DEBUFFS production renderer uses a separate root and `CustomAuraContainer` with `unit="player"` and one broad `HARMFUL` group. Blizzard owns public/private acquisition, presentation updates, sorting, pooling, FlowLayout/self-sizing, and native tooltip behavior. DEBUFFS does not register cancellation.
- The managed ENCHANTMENTS production renderer uses a third chained root and `CustomAuraContainer`. It registers native MainHand and OffHand sources through `AddItemEnchantment` and a separate managed `HelpfulEnhancements` HELPFUL aura group. Blizzard owns those managed rows' presentation state, duration, interaction, provider updates, sorting, and self-sizing. A visually matched ordinary `Fishing Lure` row is anchored below the container as an explicit exception because the managed provider cannot register the fishing profession-tool slot.
- The production managed implementation is loaded from `OdysseusBuffBars_Managed.lua` and exposed as `OBB.Managed`. MANAGED remains the architecture name and sole renderer authority.

Startup preserves existing SavedVariables adoption/defaults/normalization, calls `OBB.Managed:Initialize()`, verifies `OBB.Managed:IsReady()`, and initializes Config regardless of managed readiness. Historical unsupported raw duration/topology is evaluated into a copied runtime-only effective state before exact managed validation and is never written back. READY commits the complete B/D/E managed presentation. FAILED leaves all aura presentation inert, reports one fail-closed ERROR, attempts no alternate renderer, and permits reconstruction only through `/reload`.

### Managed readiness and protected initialization

`OBB.Managed` always exists, including on clients missing a required managed surface. `OBB.Managed:IsReady()` exposes the maintenance contract: uninitialized and initializing return false with context, ready returns true, and failed returns false with the retained fatal reason. FAILED is terminal for the session; `Initialize()` does not reconstruct the backend, public managed mutators are readiness-gated, and `/reload` is required.

Static capability validation runs before construction where possible. It checks required AuraContainer sort/direction members, FlowLayout members, item-enchantment slot/sort/placement members, safety APIs, timer APIs, HELPFUL discovery, spell metadata, and temporary-enchantment APIs. Template existence and object methods cannot be generically introspected through a supported API, so `CreateFrame`/template work and required container/AuraButton method validation occur inside the protected hidden construction boundary.

One protected initialization transaction owns complete B/D/E construction, initial AuraButton batches, event/lure/drag infrastructure, method checks, initial paired BUFFS/ENCHANTMENTS descriptor application, complete paired-snapshot verification, and presentation commit. Provisional hosts, headers, containers, and Fishing Lure presentation are retained early for containment but remain hidden; containers remain disabled. READY and managed presentation are exposed only after all required infrastructure and both initial descriptors commit successfully. Routing, filter, and classifier precedence are unchanged.

Later READY-state paired-descriptor updates retain their compensating rollback. If the new ENCHANTMENTS descriptor fails and the previous complete B/E snapshot is restored, READY is preserved and the update reports failure. If update and compensation both fail, or another required presentation commit fails, the backend enters fatal containment.

Fatal containment marks FAILED and retains the reason first, advances callback generation, clears pending managed work, unregisters/gates addon-owned managed event frames, stops active dragging, clears Fishing Lure timer/presentation state, disables/hides constructed containers, and hides hosts/headers as best effort. Named or created WoW frames may survive for the Lua session; they are not described as destroyed. Temporary unreadable HELPFUL state, combat-blocked semantic discovery, early loading-transition enchant publication, bounded native-enchantment recovery issues, and local Fishing Lure lookup/presentation issues remain degraded/retryable where their existing fallback applies rather than automatically failing the backend.

Core consumes the return from `Initialize()` and verifies `IsReady()`. Fatal managed startup prints one clear fail-closed ERROR, leaves managed presentation hidden/inert, invokes neither Engine nor any alternate renderer, and does not attempt reconstruction. Failure handling does not destructively rewrite SavedVariables; normal startup defaults/normalization and later user Config edits remain ordinary separate behavior.

### MANAGED-only renderer authority

There is no mutable authority table, per-group authority, STAGED/LEGACY mode, transition transaction, legacy pre-scan, direct-scanner fallback, or renderer-authority query/setter API. Config derives ENCHANTMENTS' fixed managed Sort/Max UI state directly from group 3. Historical E sort/max SavedVariables remain preserved but do not affect managed E runtime behavior. Copied effective duration/placement compatibility evaluation remains active and is unrelated to renderer authority.

`OBB.Managed:CommitManagedPresentation()` is readiness-gated and unconditional. At successful initialization it shows/enables all three managed hosts and containers; header visibility depends only on `anchorsShown`. Until that commit, or after fatal containment, managed hosts, containers, headers, and Fishing Lure presentation remain hidden/inert.

No Engine or Bars module/runtime surface remains. Core no longer registers or handles `UNIT_AURA`, `WEAPON_ENCHANT_CHANGED`, or `WEAPON_SLOT_CHANGED` for legacy rendering. It retains `ADDON_LOADED`, `PLAYER_ENTERING_WORLD`, and combat events required for startup, Config combat behavior, and default Blizzard-frame/Edit Mode handling. The retired Bars and Auras files and TOC entries no longer load group, header, row, timer, tooltip, positioning, addon-owned secure cancellation, direct aura scanning, scan caches/formatters, or synthetic legacy weapon-enchantment code. Managed Fishing Lure time formatting remains a private `OBB.Managed` helper. At the historical Auras-retirement checkpoint, Core's `auraData` table remained empty and `filterAuraRows` remained nil. The later Core/Config cleanup removed that empty table, the obsolete `groups`/`bars` bootstrap tables, and the guarded legacy current-row fallback without a SavedVariables or schema migration. Supported BUFF rows still come from `OBB.Managed`; unsupported group requests return no compatibility-cache rows. Focused `/reload` validation confirmed all four retired fields were nil, and no regression was reported.

Fresh-`/reload` runtime validation after Bars removal passed: MANAGED B/D/E, normal routing/presentation, native cancellation, placement, and refresh remained functional; `OdysseusBuffBars.Bars` was nil; and no duplicate, Lua error, taint, blocked action, or restricted-layout error was observed.

The formatter extraction preserved the historical 1.5-unit thresholds, upward rounding, exact suffixes, protected call, and empty-string fallback. It changed no lure discovery, profession-slot handling, duration calculation, event, 0.1-second presentation timer, expiration generation, tooltip, icon, combat-deferral, or readiness behavior. Runtime validation passed fresh login and normal managed presentation; an approximately 10-minute lure appeared, counted down stably, disappeared when the fishing pole was removed from profession equipment, and reappeared after restoration without duplicate/stale presentation or an observed Lua error. Exact 90-second, 5400-second, and 129600-second boundaries were verified statically rather than claimed as natural runtime tests.

`RefreshAll()` is the managed-only Core refresh coordinator. Slash refresh and the Config `Refresh Auras` button call it directly; the redundant `RefreshAuras()` alias is retired. `RefreshAll()` rejects missing DB or unready/FAILED managed state safely, preserves the successful framework-owned no-op in combat, and out of combat applies managed configuration before semantic/native/Fishing Lure recovery while propagating failures and return values. At the six Config Apply/filter/override sites, a successful transaction suppresses the former duplicate direct managed follow-up; a failed transaction retains the existing `ApplyConfiguration("config apply")` or candidate-filter call as a fallback. Managed-owned event recovery remains independent, and no replacement managed refresh API was added.

LibSharedMedia-3.0 owns media-name resolution for two root-level settings: `statusBarTexture` and `font`. Both are global across BUFFS, DEBUFFS, and ENCHANTMENTS, including Fishing Lure presentation, so Config Sync intentionally excludes them. Missing registrations fall back through the established default media and final literal path without rewriting the unavailable saved name. The font setting changes face only; per-group `fontSize`, count-size behavior, flags, colors, justification, anchors, and headers remain independently owned. General's compact bounded texture/font preview pickers use the Retail ScrollBox/MinimalScrollBar pattern and apply selection immediately through Config -> `RefreshAll()` -> managed `ApplyConfiguration()`.

Native item-enchantment recovery is armed on every `PLAYER_ENTERING_WORLD`, not only initial login. A temporary player `UNIT_INVENTORY_CHANGED` listener coalesces inventory activity through zero-delay generation checks; one quiet turn unregisters the listener and performs exactly one container-wide refresh. Transition epochs reject stale callbacks, and a completion reached during combat is retained for one post-combat attempt. No native enchant state is copied or reconstructed. The unchanged recovery path is runtime validated with a real MainHand weapon oil through `/reload`, loading/portal transitions, Fishing Lure coexistence, and ENCHANTMENTS configured UP; it recovered automatically without a manual diagnostic refresh and did not reset growth direction.

MainHand and OffHand are registered symmetrically through the same native provider options and recovery lifecycle. MainHand is directly runtime validated, including correct duration, native equipped-weapon tooltip, and right-click cancellation in the tested non-combat context. OffHand is source-validated and structurally covered, but no suitable active OffHand enchant was available for direct testing; OffHand-only and simultaneous-slot testing are opportunistic coverage, not an outstanding implementation requirement.

The completed naming audit used Blizzard Live source branch `live`, commit `81d15e42f16f3473131880500e7a8c8eb88fa5e6`, build `12.1.0.69404`. `C_PaperDollInfo.GetTemporaryEnchantmentInfo(slot)` exposes only `enchantID`, remaining milliseconds, charges, and expiration state. The strongest supported interpretation of `enchantID` is an internal item-enchantment identifier; no public API maps it to a spell ID, item ID, or clean localized name, so passing it to `C_Spell.GetSpellInfo` or `C_Item.GetItemNameByID` would cross identifier domains without a contract.

The native tooltip pipeline is managed item-enchantment provider -> inventory slot -> PaperDoll enchant state -> internal `itemEnchantmentID` state -> AuraButton inventory tooltip -> `GameTooltip:SetInventoryItem` -> `C_TooltipInfo.GetInventoryItem` -> already-generated localized lines. Blizzard's private inventory-tooltip generator resolves the temporary name before Lua receives the result; the UI source does not expose whether that private lookup uses a SpellItemEnchantment record, spell, item, or another table. Runtime inspection found the temporary effect as generic `TooltipDataLineType.None` (`type = 0`) text with no enchant, spell, or item ID, while a permanent weapon enchant used `ItemEnchantmentPermanent` (`type = 15`) with `enchantID`. Native weapon/slot presentation plus Blizzard tooltip context is therefore intentional final behavior, not an outstanding naming defect.

## Shared managed presentation

`InitializeManagedBarPresentation(auraButton, style)` owns only common static row construction: background, DurationBar, Icon, SpellName, DurationText, ApplicationCount, text layer, fonts, anchors, colors, icon coordinates, and native presentation-element registration. It does not own sorting, filtering, candidate groups, aura identity, duration calculations, events, cancellation policy, or host positioning. The shared presentation/header helper extraction was runtime validated on BUFFS with no observed regression before it was applied to DEBUFFS and ENCHANTMENTS.

`StyleManagedGroupHeader(header, style)` owns static header geometry, backdrop, background, border, and centered label presentation. It does not own dragging, host movement, sorting, chaining, or configuration.

All three styles begin from `260 x 18` rows, three-pixel spacing, full-coordinate `18 x 18` icons, 11-size name/duration text, 10-size outlined count text, accepted legacy geometry, and `260 x 18` legacy-style headers with a four-pixel first-row gap. Width, height, and row spacing can now change live out of combat; header height remains fixed at 18 pixels. BUFFS uses blue `{0.3, 0.5, 1.0, 0.8}` fill over `{0.0, 0.5, 1.0, 0.1}` background; DEBUFFS uses red `{1.0, 0.0, 0.0, 0.8}` over `{1.0, 0.0, 0.0, 0.1}`; ENCHANTMENTS uses purple `{0.5, 0.0, 0.5, 0.8}` over `{0.5, 0.0, 0.5, 0.1}`.

Managed rows retain native AuraButton ownership, duration text/bar, tooltips, sorting, supported cancellation, and container self-sizing. The fishing-lure exception is an ordinary row with a presentation-only local timer; its presence remains event/API driven.

## SavedVariables and configuration

Managed construction begins only after the addon has adopted SavedVariables, filled defaults, completed migrations, normalized every group, and assigned `OBB.db`:

```text
ADDON_LOADED
-> SavedVariables adoption/defaults/migrations
-> OBB.Managed:Initialize()
-> managed UI/event construction
```

`OBB.Managed:Initialize()` is idempotent. The managed Lua file does not construct containers, event frames, or the fishing-lure row at file-load time. Initialization builds a managed-runtime-owned startup snapshot with copied style/color values rather than retaining mutable SavedVariables color-table references.

Normal production Lua identifiers, audited helper parameters, current-state comments, and internal reasons use managed-renderer terminology. Exactly six `Prototype` occurrences remain as intentionally preserved global runtime frame names: the BUFFS, DEBUFFS, and ENCHANTMENTS hosts and AuraContainers. Their names remain unchanged because engine-side persistent/global frame identity and layout-cache behavior are not sufficiently proven to justify cosmetic migration. OBB placement continues to use logical group IDs and numeric coordinates, so the terminology cleanup required no SavedVariables migration, schema/API change, or compatibility shim.

An intentional SCREEN root is stored as `placement = "SCREEN"` with `anchorTo = nil`, but nil is absent from serialized SavedVariables. Previously, recursive defaults could therefore insert the D/E default parent and create contradictory state such as SCREEN plus `anchorTo = 1`; managed preflight correctly rejected that state and startup remained STAGED. Startup now records, before `CopyDefaults()`, which raw groups have an explicit placement and no parent, then restores that intentional nil parent during group normalization. No persistent discriminator or schema field was added and generic `CopyDefaults` behavior is unchanged. Missing placement plus missing parent still receives D->B / E->D defaults; explicit SCREEN without a parent remains SCREEN; malformed or unsupported graphs remain raw and are handled only by the copied runtime compatibility evaluator.

The existing configuration layer remains the only owner of control behavior and `syncGroupBars` fan-out. `showTimed` and `showTimeless` are group-local historical compatibility values rather than synchronized bar fields; only BUFFS exposes duration through one ALL/TIMED_ONLY selector. After configuration mutates SavedVariables, one centralized compatibility call reaches the managed coordinator:

```text
OdysseusBuffBarsDB
        |
existing config layer
        |
Config:Apply()
        +- OBB:RefreshAll() managed-only coordinator
        L- direct OBB.Managed:ApplyConfiguration() failure fallback
                    |
          managed presentation state
```

Config captures the `RefreshAll()` result. A successful transaction suppresses the former duplicate direct managed follow-up; a failed transaction retains the existing `OBB.Managed:ApplyConfiguration("config apply")` or candidate-filter call as a narrow fallback. The renderer-authority getter is retired.

At startup, all three managed groups consume `name`, width, height, spacing, font size, complete bar/background RGBA, icon side, scale, alpha, and growth direction. BUFFS and DEBUFFS also consume compatible saved sort and maximum-bar settings. Managed placement requires BUFFS as SCREEN; DEBUFFS may be SCREEN, BELOW, RIGHT, or LEFT of BUFFS, and ENCHANTMENTS may be SCREEN, BELOW, RIGHT, or LEFT of DEBUFFS. ENCHANTMENTS deliberately retains its separate fixed managed sort/cap behavior because one legacy value cannot exactly govern `HelpfulEnhancements`, native item-enchantment rows, and the ordinary fishing-lure row together.

Live out-of-combat synchronization covers global `statusBarTexture` and font face plus per-group `fontSize`, complete `barColor`, complete `barBgColor`, `width`, `height`, `spacing`, `iconSide`, host `scale`, and host `alpha`. Existing and future/reused managed rows use managed-runtime-owned current state. Icon-side changes reanchor retained addon-owned presentation references and recalculate the current height-derived colored boundary without enumerating AuraButtons. Scale and alpha are applied to the ordinary group hosts, so descendants inherit them without changing logical width/height. Replacement layouts preserve current geometry and ENCHANTMENTS native placement.

BUFFS and DEBUFFS live-apply Config-owned saved sort through Default/Normal, NameOnly/Normal, and ExpirationOnly/Reverse mappings, and live-apply `maxBars` through the public maximum-frame-count setter within the existing 1-80 config range. The redundant managed-header Sort buttons and their non-persistent override path are removed; `ApplyConfiguration()` continues applying existing B/D SavedVariables sort values through `ApplyManagedGroupSort()` and `SetAuraGroupSortMethod()`. All three managed containers consume saved `growUp` through TOPLEFT/Right+Down or BOTTOMLEFT/Right+Up FlowLayout while external header/chaining topology stays top-fixed. ENCHANTMENTS participates only in this growth path and remains excluded from global managed sort and maximum synchronization, retaining fixed `TIMELEFT` behavior.

Managed placement preserves the same ownership boundary. Every supported SCREEN root's saved `x`/`y` identifies its logical stack top-left; the ordinary host uses `x - 4` and `y + 22`, accounting for four-pixel host padding plus the fixed 18-pixel header and four-pixel first-row gap so the managed container resolves at the saved coordinate. Each supported BELOW child host anchors `TOPLEFT` to the parent managed container's `BOTTOMLEFT` with `saved offsetX - 4` and the saved `offsetY`; there is no 22-pixel vertical subtraction. DEBUFFS and ENCHANTMENTS hosts use `DisableUntrustedLayoutScriptsTemplate` and can switch out of combat between their supported SCREEN roots and BELOW dependencies. Startup and live apply store copied scalar applied state and reanchor only when values change. No scale/pixel conversion branch is used: scale and placement stay independent, and descendant inheritance plus declarative anchors carry growth and scale changes through the chain.

OBB SavedVariables are the sole persistent authority for those ordinary hosts. `StartMoving()` can mark a named frame as user placed, allowing WoW's frame-position cache to restore stale screen anchors over the saved BELOW graph at login. Each host is therefore made movable before `SetUserPlaced(false)` during creation, and successful drag-stop clears user-placed ownership after saving the unchanged inverse-translation coordinates. Safe post-combat restoration clears it again. The movable-first order is required because Retail rejects `SetUserPlaced(false)` on a frame that is not yet movable or resizable. No polling, container inspection, or new placement retry queue is involved.

RIGHT preserves legacy logical stack semantics without depending on physical container width. A child host anchors from `TOPLEFT` to the parent container's `TOPLEFT` at `parentLogicalWidth + offsetX - 4`, `offsetY + 22`; D uses the applied BUFFS width and E uses the applied DEBUFFS width. LEFT anchors to the same point at `offsetX - 4 - childLogicalWidth`, `offsetY + 22`; D uses its applied DEBUFFS width and E uses its applied ENCHANTMENTS width. Applied RIGHT/LEFT state retains the relevant logical width, so live parent-width or child-width changes reapply the correct relationship. No `GetWidth()`, AuraButton enumeration, scale compensation, fake minimum, or manual container sizing is used.

Supported raw states are consumed exactly. Historical unsupported raw topology is copied and interpreted only for managed rendering: invalid BUFFS becomes SCREEN using usable saved numeric x/y, invalid DEBUFFS becomes BELOW BUFFS at `0,-8`, and invalid ENCHANTMENTS becomes BELOW DEBUFFS at `0,-8`. The evaluator records each raw/effective difference and exposes only copied compatibility state. A synthetic compatibility SCREEN cannot be dragged/persisted until the user explicitly selects supported placement. Each real supported SCREEN root remains independently draggable out of combat and unlocked; drag-stop applies inverse translation to shared `x`/`y`, records copied applied state, and clears user-placed ownership without a legacy positioning dependency. Anchored BELOW/RIGHT/LEFT groups retain their parent warning. `Reset Positions` keeps its prior SavedVariables semantics and normal single `Config:Apply()` path.

The intentional production topology is exact: BUFFS is the SCREEN root; DEBUFFS is either SCREEN or BELOW/RIGHT/LEFT of BUFFS; ENCHANTMENTS is either SCREEN or BELOW/RIGHT/LEFT of DEBUFFS. Config offers only those choices, so it cannot newly create ABOVE, arbitrary-parent, reverse, or cyclic graphs and no longer calls `BreakAnchorCycleForTarget()` from this path. Historical unsupported values remain visible with an inline warning until explicit correction; opening or refreshing Config and unrelated controls do not rewrite them.

ABOVE is intentionally unsupported in the managed architecture and retired from current Config choices. BELOW works because the child's external host can depend declaratively on the parent's dynamic bottom. RIGHT and LEFT require only stable internal logical widths. ABOVE instead requires the child's Blizzard-owned dynamic bottom/full visible height to drive its own external host position. The Live source audit (`live` at `81d15e42f16f3473131880500e7a8c8eb88fa5e6`) found no public CustomAuraContainer post-layout/size callback or safe active displayed-count scalar; `OnSizeChanged` is unavailable under `UntrustedLayoutScriptExecution`, geometry accessors are secret-aware rather than a content-height contract, and polling/private hooks/duplicated row-height logic would create a second height authority. ENCHANTMENTS also has incomplete container bounds because Fishing Lure is outside the container. A historical raw ABOVE value remains untouched and uses the appropriate copied canonical fallback without claiming visual-location equivalence.

### Managed header and retired Bars boundary

`anchorsShown` controls all three addon-owned managed header Buttons. `OBB:ToggleAnchors()` mutates that normal setting and sends one narrow managed visibility notification; no full managed configuration apply is required. Hiding is visibility-only: it neither moves hosts or containers nor reclaims the fixed header reservation, changes SCREEN/BELOW/RIGHT/LEFT placement or saved coordinates, alters growth/scale, hides aura rows or Fishing Lure, or touches managed AuraContainers. Hidden Buttons provide no drag input; showing them restores the existing SCREEN-root drag behavior. `locked` and Blizzard default-frame visibility remain independent.

The former `showLegacyBars` and `legacyComparisonMode` fields are no longer production defaults and have no production Lua reader or writer. New/default databases do not receive them. Existing serialized copies remain preserved and ignored by the non-destructive defaults path; focused runtime validation retained this user's historical `showLegacyBars=false` and `legacyComparisonMode=true` without affecting managed operation. No migration, purge, schema change, or destructive SavedVariables rewrite was introduced. Historical D/E filters, duration data, E sort/max, placement values, and unknown keys likewise remain preserved without migration. The active copied duration/placement compatibility evaluator is independent and unchanged.

Managed HELPFUL candidate admission has one authoritative composition path. Managed-runtime-owned semantic `HelpfulEnhancements` membership, existing numeric `hidden`/`group = "BUFFS" | "ENCHANTMENTS"` overrides, BUFFS destination filters, and supported BUFF duration state compile into complete BUFFS and `HelpfulEnhancements` descriptors. The two public setters are invoked together and the last successfully applied complete descriptor snapshot is copied only afterward. Managed ENCHANTMENTS filter tables neither seed ownership nor restrict `HelpfulEnhancements` eligibility.

For every relevant numeric HELPFUL ID, effective ownership resolves in this order: hidden, explicit group override, semantic enhancement route, then default BUFFS. Hidden removes an ID from both managed HELPFUL groups, and deleting an override restores semantic/default ownership. Only BUFFS applies destination filtering after ownership: an active whitelist ignores its blacklist and admits whitelisted effective-B IDs; otherwise its blacklist rejects matching effective-B IDs. ENCHANTMENTS has no destination whitelist/blacklist stage and includes every effective-E ID. Ownership and destination filtering are separate policies.

Managed filtering is final and group-specific. BUFFS alone exposes Whitelist/Blacklist and the supported ALL/TIMED_ONLY duration selector. Managed DEBUFFS remains broad across eligible Blizzard-managed player HARMFUL auras while retaining sort, `maxBars`, presentation, and layout behavior. Managed ENCHANTMENTS remains broad across `HelpfulEnhancements`, native MainHand, native OffHand, and Fishing Lure; its 7+2+1 source policy is unchanged. D/E expose neither Whitelist/Blacklist nor duration controls. Their shared Config construction anchors Icon below Sort with normal spacing because they omit the BUFF-only filter controls; BUFFS keeps its side-by-side Sort/Icon layout.

The same effective-route resolver owns candidate compilation and the runtime current-HELPFUL ownership projection. During guarded out-of-combat discovery, the managed runtime replaces a runtime-only snapshot of currently active readable numeric spell IDs plus available safe name/icon metadata. Its accessor computes B/E ownership from semantic state and overrides and returns copied rows sorted by spell ID; BUFFS uses that projection for its `Current group auras` UI, while E ownership remains routing state rather than an exposed destination-filter editor.

BUFFS current rows contain only effective BUFFS-owned readable HELPFUL IDs. Internal effective-E ownership still includes semantic enhancements and explicit B->E overrides, and hidden IDs have no B/E ownership, but ENCHANTMENTS no longer exposes a destination-filter editor. Save/Delete override actions retain immediate ownership recomposition; routing support was not removed.

Editor opening/rendering reads the BUFFS snapshot. Existing discovery refresh paths remain unchanged; no polling, ticker, new `OnUpdate`, retry queue, AuraButton enumeration, or private collection access was added. D/E historical filter tables and cache data remain preserved for compatibility/history, but managed D/E neither expose nor consume those destination filters. No defaults or schema changed.

Managed BUFF duration admission supports two states without addon-side aura-duration reads. ALL (`showTimed=true`, `showTimeless=true`) omits `maxDuration`; TIMED_ONLY (`true`, `false`) uses `maxDuration = math.huge`, letting Blizzard reject zero-duration permanent/timeless candidates while admitting positive finite original durations. Historical TIMELESS_ONLY (`false`, `true`) and NONE (`false`, `false`) remain raw but the effective copied state is always ALL until explicit Config correction. The Config selector offers only ALL/TIMED_ONLY. These compatibility branches are implemented and source/static validated but were not deliberately runtime injected in Phase 2 testing.

Managed DEBUFFS intentionally remains broad and always admits timed plus timeless HARMFUL state; this preserves potentially important mission, encounter, raid, or Mythic+ debuffs. General HARMFUL identity restrictions reinforce the decision, but broad visibility is now the product policy rather than an unresolved parity gap. Managed ENCHANTMENTS likewise admits all eligible timed and timeless sources and intentionally has no per-ID destination filtering.

The managed DEBUFFS group intentionally does not use candidate spell-ID maps or expose the historical DEBUFFS filter editor. Existing saved numeric IDs remain intact as compatibility/history data. This is the finalized managed product policy, not missing parity.

Managed ENCHANTMENTS uses a deliberate 7+2+1 capacity policy: seven `HelpfulEnhancements`, two registered native providers (MainHand and OffHand), and one ordinary Fishing Lure footer. Fishing Bobber is a HELPFUL aura and consumes one of the seven aura slots; it is not the lure footer. Native enchantments use `AfterAuraGroups` placement and Slot/Normal ordering, producing the DOWN order HelpfulEnhancements, MainHand, OffHand, then Fishing Lure. In UP mode Blizzard reverses spatial progression while preserving logical source sequence, so native rows move toward the header and `HelpfulEnhancements` occupies the lower managed portion. The ordinary lure stays below the container as a fixed footer outside FlowLayout in both directions. Ranged is not registered. Legacy ENCHANTMENTS sort/`maxBars` remain stored for compatibility but are intentionally ignored by the managed policy; no schema change was made.

An empty managed container may collapse to its approximately `1 x 1` managed bound, unlike the legacy renderer's one-row minimum. BELOW follows that actual bound; RIGHT/LEFT use logical width so empty physical width cannot cause lateral jumps. No fake minimum or manual sizing is added. ENCHANTMENTS is terminal in the supported graph because its ordinary Fishing Lure footer is outside the managed container and therefore outside that container's bounds. A future downstream parent/full-visible-bounds design remains research work.

Retail validation confirms the final controls and policies: BUFF filtering is unchanged; BUFF duration offers only ALL/TIMED_ONLY; B/D/E anchor and placement choices are constrained to the production graph; D/E stay broad; and semantic routing, native rows, Fishing Lure, combat/loading behavior, and managed-only refresh remain functional. Final production validation covered fresh login, `/reload`, many World Quests and Delves, heavy simultaneous aura populations, correct routing, and no duplicate legacy presentation or observed OBB Lua errors. Historical TIMELESS_ONLY/NONE, invalid B/D/E parent, ABOVE, SCREEN+parent, and explicit cycle states were not deliberately injected. Authority switching and managed-to-legacy position synchronization are retired. The later atomic production rename to `OdysseusBuffBars_Managed.lua` / `OBB.Managed` and internal managed-renderer terminology cleanup changed no runtime semantics or SavedVariables/schema/API. Focused terminology-checkpoint validation passed `/reload`, retained correctly positioned B/D/E and normal managed behavior, and confirmed Config sorting plus visible BUFFS/DEBUFFS Sort-button label synchronization with no observed runtime regression.

## Combat restrictions

Managed aura updates, duration presentation, sorting, and already-applied candidate filters continue to operate during combat. Drag start, placement mutation, sort changes, BUFFS filter mutation, HELPFUL enhancement rediscovery, and fishing-lure API refreshes are blocked or deferred during combat. An active managed drag interrupted by combat is stopped without saving and restored to its prior applied SCREEN point after combat. This narrow restoration is separate from pending routing/lure/native-enchantment recovery and is not a general placement queue.

`OBB.Managed:ApplyConfiguration()` also refuses managed presentation mutation during combat and returns `false, "combat lockdown"`. It does not queue or defer configuration changes. The normal configuration UI already prevents its mutation paths during combat; this is not combat-capable live restyling.

The native-enchantment transition recovery is the narrow exception to the no-deferred-configuration statement: if its one-shot completion reaches combat, that recovery alone may finish after `PLAYER_REGEN_ENABLED`. This does not create a general configuration queue.

The permanently disabled local automatic HELPFUL-routing debug gate and trace layer are removed. Routine automatic routing remains silent, while unexpected discovery/filter failures remain visible; no SavedVariables debug setting exists.

Current operational/field diagnostics are intentionally exposed through `OBB.Managed`, including `ClassifyHelpfulEnhancement`, `DumpHelpfulEnhancementClassifications`, `DiscoverAndApplyHelpfulEnhancementRouting`, and `DumpFishingLureState`. For semantic-routing discovery, use `/run OdysseusBuffBars.Managed.DiscoverAndApplyHelpfulEnhancementRouting()`. The isolated fixed-ID tooltip/spell metadata research inspector is retired.

The retired legacy direct scanner could become unavailable or secret in Retail 12.1 combat. Its historical limitations are preserved as migration context and are not managed-frame failures.

## Retail 12.1 transition

- Managed BUFFS, DEBUFFS, and ENCHANTMENTS are the sole production renderer after READY. Startup is READY-or-FAILED; fatal initialization retains FAILED readiness and disables aura presentation for the session without legacy fallback. The strict effective-state checks formerly performed by authority preflight now run inside managed initialization.
- Managed DEBUFFS remains intentionally broad and non-cancellable. This checkpoint does not claim targeted private-HARMFUL coverage.
- Managed ENCHANTMENTS has validated MainHand behavior, bounded loading/world-transition recovery, FOOD/FLASK_PHIAL/AUGMENT_RUNE/FISHING_BOBBER routing, and the ordinary fishing-lure lifecycle. Native weapon rows support right-click cancellation; the lure footer does not. OffHand uses the same source-validated registration/recovery structure, while direct OffHand-only and simultaneous-slot behavior remain opportunistic runtime coverage because no suitable test enchant was available. Combat cancellation, permanent/zero-duration behavior, Ranged where exercisable, and broader native enchant families remain pending. A clean temporary-enchant effect name is not available through the supported public contract and is not treated as a pending scraping or compatibility-table feature.
- Blizzard Edit Mode owns default Aura Frame visibility, and its `Hidden`
  setting is the supported user-facing policy. OBB's `Hide default Blizzard
  frames` setting is a best-effort out-of-combat convenience that is reapplied
  after Edit Mode closes; it does not replace Blizzard's update or combat
  visibility ownership.
- The duplicate Config refresh/application audit, atomic production file/namespace rename, internal managed-renderer terminology cleanup, redundant BUFFS/DEBUFFS Sort-button removal, diagnostic retention/removal cleanup, updated Live AuraContainer/private-aura source review, first public-release repository housekeeping, v1.0.0 version/build metadata, fuller first-release documentation, final static release validation, and final LIVE v1.0.0 sanity test are complete. Static validation passed every established LuaCheck baseline and `git diff --check` with no release blocker; the user-reported LIVE-only sanity test passed with the addon working correctly and no release-blocking runtime issue. No PTR release-gate test was required. The retained transient-failure fallback was verified statically rather than deliberately injected. The annotated `v1.0.0` tag and push, curated installable ZIP and GitHub Release, post-release verification, any evidence-driven frame-name migration, broader native lifecycle coverage, deliberate historical compatibility injection, full ENCHANTMENTS bounds, and Config polish remain pending.
- Detailed architectural history, including the retired rollback modes and their validation boundaries, is preserved in `MANAGED_AURACONTAINER_MIGRATION.md`.
